# Blutbild-Buddy — Agent Instructions

## Quick commands

```bash
streamlit run app.py                        # Dev server
python test_blutbild_buddy.py               # All tests (unittest)
docker compose up -d                        # Docker deployment
```

## Gotchas (easy to get wrong)

- **Streamlit + Starlette pin**: `streamlit==1.58.0` must stay paired with `starlette==1.3.1` in `requirements.txt`. Newer Starlette requires a `thread_minimum_size` param that older Streamlit doesn't pass.
- **DB lives at `data/blutbild_buddy.db`** (relative to project root), NOT `blutbild_buddy.db` in the repo root. `.gitignore` covers both paths but they're different files.
- **Docker LLM default**: `LLM_BASE_URL` defaults to `http://172.17.0.1:8888/v1` (Docker bridge network), not `localhost`. Override via `.env`.
- **Tests patch by value**: Test setup does `config.DB_PATH = temp_path`. This works because other modules import specific names from config (`from config import DB_PATH`) rather than the module reference. Don't change this pattern.
- **LLM env vars are read lazily** in `config.py` (via getter functions). Changes to `os.environ` after import *are* picked up. This is intentional for the in-app Settings dialog.
- **Risk flags are idempotent, but SCOPED**: `refresh_risk_flags()` does DELETE + INSERT from scratch each call. The DELETE is scoped to the passed `patient_id`'s own reports — a global delete (the old behaviour) wiped every other patient's cards when one patient clicked refresh. Every UI trigger passes the selected patient; `patient_id=None` is only the all-patient pass (tests, startup rebuilds).
- **Strict per-patient separation (the multi-user rework)**: the patient picker IS the identity — nothing cross-patient renders, and every write is scoped to the selected patient. The seams that used to leak:
  - **Uploads are bound to a patient** via the `PendingUpload` table (`pending_uploads`, filename unique, `patient_id` NOT NULL). `_handle_file_upload(patient_id)` refuses an upload with no patient selected (`_upload_needs_patient` → warning) and records one `PendingUpload` row per saved file. `process_new_pdfs(patient_id=)` reads ONLY that patient's pending rows (never the shared folder glob) and files the report under the **uploader**, ignoring the name read off the PDF — a misread name can never move data to someone else. `remove_pending_upload` runs after each successful commit; a failed extraction keeps the row for retry.
  - **`LlmJob.patient_id`** (denormalised from `params["patient_id"]` at submit) keys the **kind lock** as `(kind, patient_id)` in `llm_jobs._active_kinds`, so patient A's running job never disables patient B's button. `list_llm_jobs`/`get_active_llm_jobs`/`clear_finished_llm_jobs` all take `patient_id` and filter `(patient_id == X) | (patient_id IS NULL)` — app-level kinds (`test_connection`) and legacy NULL rows stay visible to everyone. The LLM-Jobs tab is scoped to the selected patient.
  - **Registry edits stay global on the ROW but scoped on the DATA**: `update_biomarker_registry`/`_mutate_registry_row`/`_merge_registry_rows`/`_migrate_name_rows` all take `patient_id`. A rename updates the shared `BiomarkerRegistry` row (reference data) and keeps the old name as an alias, but migrates only the acting patient's `DataPoint`/`BiomarkerInfo` rows — other patients keep the old name and their own Mapping tab surfaces it as unregistered. `backfill_reference_ranges(patient_id=)` writes only that patient's rows.
  - **`delete_patient(session, patient_id, delete_pdf_files=)`** is the destructive admin counterpart to merge (Patients tab, type-the-name-to-confirm dialog). SQLite doesn't enforce FKs and the ORM cascade only covers declared `Patient` relationships, so it explicitly deletes risk_flags, data_points, artifacts (by report id), findings, chat_messages, chat_conversations, summaries, biomarker_infos, pending_uploads, llm_jobs, reports, then the patient. **Report filenames MUST be captured before the report rows are deleted** — the PDF-cleanup loop re-queries `Report.filename`, and after the delete it finds nothing (this was a real bug: `delete_pdf_files=True` silently kept every PDF). A PDF is only deleted when no other patient still references the same filename. The returned `counts` dict is **seeded with every key at 0** — the conditional deletes must never omit keys, because the Patients tab success message reads `result["data_points"]`/`result["reports"]` unconditionally (a report-less patient used to crash it with `KeyError` *after* the delete had already committed). Pinned by `TestPatientIsolation`.
- **Patient names normalize to "LastName, FirstName"** via `database.normalize_patient_name()`. Handles formats like `Doe J.` → `J., Doe`, underscores, commas.
- **Biomarker merge groups** are keyed by `(case-insensitive base name, normalized unit)`. `normalize_unit()` lowercases AND collapses internal whitespace, so `ml/ min` == `ml/min` (a stray OCR space no longer splits one marker into two). Genuinely different units (e.g. `mg/dl` vs `mmol/l`) still prevent grouping. `clean_unit()` (storage-side) strips all whitespace runs; the extractor cleans units at ingestion, and `_migrate_clean_unit_whitespace()` fixes legacy rows once. Every other unit-writing path also cleans first (`clean_unit`): `set_unit`/`set_ref_range` data-quality fixes, `apply_merge_plan` target units, `_parse_ref_range`, registry `unit` edits (`_mutate_registry_row`). `config._norm_unit()` also collapses whitespace, so the conversion/equivalence tables need no per-spacing entries (`_UNIT_EQUIV` has no `ml/ min` band-aids).
- **Unit hygiene at ingestion (the three config helpers, all value-preserving)**: the extractor now runs `unit = sanitize_unit(entry.unit)` → resolve canonical → `unit = canonicalize_unit(canonical, unit, registry)` (NOT `clean_unit` — that only strips spaces). `sanitize_unit` ALSO drops a leaked column-header word (`"Unit"`, `"Einheit"`, `"Referenzbereich"` — the live DB literally stored `"Unit"` as a unit) and punctuation-only placeholders (`-`, `n.a`), returning `None` so the registry default range applies. `canonicalize_unit` snaps a unit to the marker's own registry spelling when the rewrite is value-preserving: case/spacing drift (`ML/ MIN`→`ml/min`) or a notation variant in the same `_UNIT_EQUIV` group (`Tsd/µl`→`10³/µl`, `/pl`→`Mio./µl`, `ng/l`→`pg/ml`, `ml/min/1.73`→`ml/min/1.73m²`). It NEVER rewrites a category error or an ambiguous fragment. `_migrate_unit_notation_cleanup()` applies the same snap to existing `data_points` once (idempotent; leaves category errors for the guard). `unit_known_for_marker(canonical, unit, registry)` is the **category-error guard**: returns False ONLY when the unit is a recognised lab unit for SOME marker but incompatible with THIS one (ALT/AST in `mg/dl`, Glukose/Harnsäure in `U/l`) → the extractor emits a `category="unit"` / `action="set_unit"` finding (params = the marker's first registry unit). It stays SILENT (True) on: an empty unit, an **unregistered** marker (no registry units to contradict — do NOT flag a made-up name just because its unit matches another marker), a bare ambiguous denominator (`/l`, `/ml`, `/µl` — magnitude-ambiguous, e.g. Thrombozyten `/ul` must NOT false-flag against Leukozyten `/µl`), and any unit the marker does list. `_UNIT_EQUIV` has `ml_per_min_173` (`ml/min/1.73m²`/`m2`/bare `1.73`) and `pg_per_ml` (`ng/l`==`pg/ml`) groups; `ml/min` stays its OWN group (different quantity — never collapse into `1.73m²`). `_UNIT_CANONICAL_DISPLAY` gives a display spelling when a marker lists no unit in the group.
- **`set_unit` fix is plausibility-aware** (`database._value_implausible_under_old_unit`): accepting a `set_unit` finding RELABELS (keeps the number) instead of converting when ALL hold — the OLD unit is foreign to the marker, the NEW unit is native, and the value fits the new unit's default range within a wide ×10/÷10 tolerance. That is the live-DB ALT-in-`mg/dl` case (value 33 is enzyme-scale; converting would invent a wrong number). A legitimate change still converts (Glukose 100 `mg/dl`→`mmol/l` — 100 is plausible under the native `mg/dl`). A notation variant (`/nl`→`10^3/µl`) relabels via `_units_equivalent` before either branch. Pinned by `TestSetUnitRelabelIfImplausible` + the six pre-existing `test_set_unit_*` tests.
- **A `set_unit` proposal can go STALE after a rename** (`_apply_data_point_fix`, helper `_unit_matches_marker_units(unit, reg_units)` — strict: the unit matches one of the marker's OWN registry units via `_norm_unit`/`_units_equivalent`; `_value_implausible_under_old_unit` reuses it): the live case — an ambiguous `Testosteron` resolved to `Testosteron gesamt` (units `ng/dl`/`nmol/l`), so the unit guard flagged the row's `pg/ml` and proposed `set_unit→ng/dl`; the user then RENAMED the marker to `Testosteron frei` (units `pg/ml`/`pmol/l`), where `pg/ml` is CORRECT and `ng/dl` is foreign. When `_convert_ref_range` returns None (it sits INSIDE `if conv_value is None:`, so supported conversions always proceed), classify: OLD unit native AND NEW unit foreign → stale post-rename proposal → count `stale`; if nothing applied return the detail "the proposed unit is not a unit this marker is measured in — the marker was likely renamed after this finding was created. The stored unit looks correct; use the manual correction below instead." (NOT the misleading "unsupported unit conversion"). The stored value/unit are left untouched. Pinned by `TestApplyDataQualityFinding.test_set_unit_stale_after_rename_reports_renamed`.
- **Unit-qualified name variants (`HbA1c (%)` vs `HbA1c (mmol/mol)`)**: some canonical names embed the unit in the trailing parenthesis. Four config helpers (registry-driven, config never imports database): `marker_base(name)` strips the trailing parenthetical (mirrors `database._canonical_base`); `embedded_unit(name, registry)` returns the unit ONLY if the parenthetical actually IS a unit for this marker — None for abbreviations like `ALT (GPT)`, `Hämoglobin (Hb)`, `Vitamin D (25-OH)`; `name_has_unit(name, unit, registry)` is equivalence-aware; `resolve_unit_qualified_variant(canonical, unit, registry)` snaps a row to the sibling variant whose embedded unit matches the row's unit — fires ONLY when both names are unit-qualified variants of one base, the unit is incompatible with the current name, and exactly one sibling matches; renames only, NEVER converts value/unit/ref.
  - **The guard runs in BOTH extraction phases**: phase 1 (per-PDF, deterministic alias resolution) right after `canonicalize_unit`, and phase 2 `_normalize_names_pass` on `new_canon` BEFORE the `if new_canon == dp.canonical_name: continue` check — phase 2 is the load-bearing half, because the LLM mapping pass is what rewrote bare `HbA1c` alias hits into the wrong variant (`HbA1c (mmol/mol)` holding a `%` value, live-DB ids 730/830/889). Pinned by `TestUnitQualifiedVariantExtraction`.
  - **Display labels go through `ui/helpers.marker_label(cname, unit)`** — the single source of truth: it appends `({unit})` only when `not config.name_has_unit(...)`, so `HbA1c (%)` + `%` no longer renders as `HbA1c (%) (%)`. Overview favorites, the deviation chart, the All-Values matrix and the XLSX export all route through it (watch for a local variable shadowing the import). Gotcha: favorites are persisted in `Patient.favorites` as these exact label strings — changing the label format silently drops stored favorites (live DB: both patients had `favorites=None`, so no migration was needed).
  - **The Trends picker is two-level**: `trends.py` groups the patient's `(canonical_name, unit)` storage pairs by `marker_base(cname) or cname`; the marker selectbox (`trends_marker_{id}`) lists each base name ONCE, and a second selectbox `Einheit / Variante` (`trends_unit_{id}_{base}`) renders only when that base has >1 variant (single group → no second widget, avoiding a block-count shift). `_unique_variant_label` labels variants honestly: clean `marker_label` when the stored unit matches the name, `— ohne Einheit` when unit is None, `— gespeicherte Einheit: <unit>` when the stored unit drifts from the name (legacy drifted rows), `· #N` suffix only as a last-resort collision net. The drifted live-DB rows were deliberately NOT migrated (user chose to hand-fix them in the Mapping tab) — new PDFs can no longer produce the drift. Pinned by `TestUiBehaviourAppTest.test_unit_qualified_variants_group_under_one_marker` / `test_single_group_marker_shows_no_unit_subpick`.
- **Streamlit 1.58 CSS vars are NOT defined**: `--secondary-background-color`, `--border-color`, `--text-color` do NOT exist as CSS custom properties in Streamlit 1.58 (getComputedStyle → empty string), so `var(--border-color)` silently renders nothing (invisible borders/backgrounds). `ui/cards.py` uses plain `rgba()` fallbacks followed by `color-mix(in srgb, currentColor N%, transparent)` overrides. Don't reintroduce `var(--…)` in card CSS.
- **Conditional blocks ABOVE the tab bar reset the selected tab (the job-strip regression)**: Streamlit identifies a block by its **delta path** — its index among its siblings — and the frontend keys a tab bar's React component (which owns the selected tab) by exactly that path. An **unkeyed** `st.tabs()` keeps its selection ONLY in React `useState`; the backend re-sends `default_tab_index = 0` on every run. So when the running-jobs strip renders a variable number of blocks above the tab bar (0 while idle, ≥1 while a job runs), the strip appearing (job start) or vanishing (job finish) shifts the tab bar one slot, React remounts it, and the user is thrown back to the first tab (Übersicht — looked like "the app jumps to the dashboard on every job"). The fix has BOTH halves and both are load-bearing: the strip renders into an ALWAYS-created `st.container()` (constant block count above the tab bar) **and** both tab bars carry a user key (`_main_tab_bar`, `_mgmt_tab_bar`) — a key gives the block a stable id, which is what makes the frontend persist/restore the active tab label via the widget manager's element state (`getElementState(blockId, "activeTabLabel")`, only consulted when the block HAS an id). Rule: any block whose presence is conditional must not change the number of siblings above other content — give it a permanent container slot and/or key the widgets below. Pinned by `TestUiBehaviourAppTest.test_tab_bar_position_stable_when_a_job_starts` (compares the main-container child index of the `tab_container` block with and without a pending job, and asserts `tab_block.proto.id` is non-empty; fails `[3] != [4]` without the fix).
- **Render DPI is page-box-relative, not scan-relative** (`pdf_processor._render_scale`): `page.render(scale=dpi/72)` scales against the PDF **page box (MediaBox in points)**, NOT the embedded scan. A scanner that shrink-wraps its output writes a tiny MediaBox (e.g. `210×280` pt = 2.9×3.9 in) around a high-res embedded JPEG (1500×2000 px ≈ 514 effective DPI) — rendering that at "200 DPI" yields only **583×778 px** and silently discards ~70% of the linear detail, so small digits become unreadable and the model misreads cells (it read the reference column's first number as the measurement). Normal A4/Letter pages have a ~595×842 pt box, so 200 DPI already renders ~1650×2360 px and is **unaffected**. The fix: when a page box's long side < `_SMALL_PAGE_LONG_PT` (500 pt), boost the scale to the embedded image's native DPI (`PdfImage.get_px_size()` / `get_bounds()`), capped at `_MAX_BOOSTED_LONG_PX` (2400) to bound the base64 payload. `pdf_to_images` and `pdf_to_base64_jpeg` both route through `_render_scale`. Pinned by `TestRenderScale` (small-box fixture renders at native 1500×2000; A4 box keeps exactly `dpi/72`).
- **Markdown + HTML in one `st.markdown` call**: a chunk that starts with a raw HTML tag is parsed by Remark as ONE opaque HTML block — markdown glued into the string renders literally (`##` stays `##`). `ui/cards.render_markdown_card()` is the single helper for markdown-inside-a-card: it separates `<div>` and body with **blank lines** (`<div>\n\n{md}\n\n</div>`) and escapes only `&`/`<` (never `>`, or blockquote markdown dies; `html.escape()` is wrong here). Risk cards in `ui/tabs/risks.py` deliberately keep inline HTML — their fragments are pre-escaped HTML, not markdown.
- **Column-confusion guard (the extractor's signature failure)**: a lab table has one name column, ONE reference column, and often SEVERAL result columns (one per draw date). A vision model silently reads the reference cell as the measurement, or collapses a multi-column report into one series. The fix is structural: the extraction prompt makes the model **declare the table layout first** (`ExtractedPage.columns`, each a `TableColumn` with a `role` name|result|reference|unit|flag and an optional `result_date`) and **tag every entry with its result column** (`BiomarkerEntry.column_index`). `schemas._normalise_column_role` coerces messy role words; `BiomarkerEntry.value_raw` keeps the printed value string whenever the model returned a string (ALWAYS now, not only when coercion lost content — so the Mapping tab can show the exact reading `13,18` beside the parsed `13.18`, and a range-shaped string coerced to `None` stays recoverable). `extractor._page_layout`/`_entry_series`/`_column_findings` validate the declaration **deterministically** (9 checks: value-is-range swap, ref-holds-bare-number, degenerate `ref_low==ref_high`, entry pointing at a non-result column, >1 reference column, a name missing from some result columns, a **systematic** `value == own ref bound` pattern (the low-res misread signature, see `_MIN_BOUND_MATCHES`/`_MIN_BOUND_FRACTION`), a **unit category error** (see the unit-hygiene bullet), and a **low-confidence entry** — `BiomarkerEntry.confidence < _LOW_CONFIDENCE_THRESHOLD` (0.5), only when the model actually emitted one) and emit pending `DataQualityFinding`s — **never applied silently** (which cell was right isn't always decidable from stored data; the user confirms in the Mapping tab). A page with **no declared columns** degrades to the old flat behaviour (no layout checks), so a weaker model still produces data.
- **`BiomarkerEntry.confidence`** (opt-in, 0..1): the extraction prompt (single + batch) asks the model to add a per-entry `confidence` ONLY for a cell it had to guess at (blurry/overlapping/unclear digit) and to omit it otherwise — never pad with 1.0. `schemas._normalise_confidence` coerces it (number >1 read as a percentage, word map high→0.95/unsicher→0.4/low→0.3, unrecognisable→None); a `None` is NEVER flagged. The extractor turns a sub-threshold value into a `category="value"` / `action="acknowledge"` finding. **The description MUST quote the suspect reading + its reference range** (`extractor._fmt_reading` prefers `value_raw` so the description shows the SAME text the scan shows, e.g. `13,18`, falling back to the parsed number then `—`): a finding that names only the marker + confidence makes the source-page image useless — there is no number to compare the scan against. Pinned by `TestEntryConfidenceAndRaw` + `TestUnitGuardExtraction.test_low_confidence_creates_acknowledge_finding` / `test_low_confidence_description_shows_reading`.
- **`DataQualityFinding.source_page`** (nullable Integer, 1-based): the report page the affected entries came from. Set by the extractor (`page_idx + 1`) and the verify job (`_verify_problem_to_finding(..., source_page=page_idx+1)`); NULL for the on-demand check (reasons over stored data, no page) and report-level findings. The Mapping tab renders that page's image in an expander beside the finding via `ui/queries.report_page_image(report_id, filename, page)` — a `@st.cache_data` helper wrapping `pdf_to_base64_jpeg`, deliberately keyed on `(report_id, filename, page)` NOT the cache token (a report's PDF is immutable; a reprocess makes a new id), so unrelated DB writes never bust an expensive render. Returns `None` when the file is gone / page out of range → the tab shows `caption_finding_source_missing` instead of crashing. Migration `_migrate_data_quality_findings` adds the column (nullable).
- **`DataPoint` rows MUST be flushed before their `.id` is read**: the extractor builds a finding's `data_point_ids` from `dp_by_pos[p].id`, so `session.flush()` runs after the page's DataPoints are added and before `_column_findings`. Without it the ids are `None`, `data_point_ids` becomes `[null]`, and an accepted swap can never be applied (`apply_data_quality_finding` → `skipped`). Pinned by `TestColumnConfusion.test_value_is_range_creates_swap_finding`.
- **`DataQualityFinding.source`** (`"check"` | `"extraction"` | `"verify"`, default `"check"`): the three producers are the on-demand data-quality check, the deterministic extractor checks, and the second-pass auditor. `clear_patient_data_quality_findings(session, patient_id, source=)` is scoped by source; the reprocess job deletes `source.in_(["extraction","verify"])` (a re-extract regenerates both), and the verify job deletes only `source=="verify"` for the reports it audits (idempotent — re-running replaces its own findings, leaves extraction + check findings untouched).
- **`Report.raw_text` is JSON**, not the old flat repr: `json.dumps({"pages":[{"columns":[...], "entries":[e.model_dump()...]}...]}, default=str)`. Nothing parses it for display — it exists so the verify job (`_parse_raw_pages`) can re-send the exact layout + entries the model produced without re-extracting. Reports extracted BEFORE this change have the old flat repr → `_parse_raw_pages` returns `[]` → the verify pass skips them.

## Architecture (one file per concern)

Declares + validates the table layout per page (`_page_layout`/`_entry_series`/`_column_findings`). Unit-qualified variant guard runs in BOTH phases (`resolve_unit_qualified_variant`: phase 1 after `canonicalize_unit`, phase 2 in `_normalize_names_pass`) |
| `analyzer.py` | Risk flag engine: out-of-range, trending, volatility, missing markers, cross-biomarker correlation rules. `refresh_risk_flags()` ranks findings with the LLM **per patient** (one `assess_risks` call per patient) |
| `llm_client.py` | OpenAI-compatible client calls (extract + normalize + summarize + chat + **verify**), embedded system prompts |
| `pdf_processor.py` | pypdfium2 → JPEG images, base64 encoding, SHA-256 hashing |

| `ui/queries.py` | Cached read-only query layer for the tabs: `@st.cache_data` helpers returning ORM-free namedtuples, keyed on `cache_token()` |

| `schemas.py` | Pydantic models for LLM JSON responses (`TableColumn`, `VerifyProblem`/`VerifyPageResult`) |
| `config.py` | Paths, lazy env-var getters, ~94 biomarker registry (canonical names, aliases, default ref ranges), risk thresholds & cross-biomarker rules, unit hygiene + unit-qualified name-variant helpers (`marker_base`, `embedded_unit`, `name_has_unit`, `resolve_unit_qualified_variant`) |
| `translations.py` | DE/EN translation dictionaries and helpers |
| `test_blutbild_buddy.py` | Single-file unittest suite — mocks LLM calls for extractor/analyzer tests |

## Key patterns

- **Column-aware extraction + multi-series (the column-confusion feature)**: a report page can carry SEVERAL result columns (one per draw date) plus ONE reference column. The extractor declares the layout (`ExtractedPage.columns`) and tags each entry (`column_index`); `_entry_series` turns a tagged entry into its `(result_date, column_label)`, which is stored on `DataPoint.result_date` (DateTime) / `DataPoint.column_label` (String). A report whose result-column headers were dates records them (JSON list) on `Report.result_dates`. Single-column reports keep both `DataPoint` fields NULL and `result_dates` NULL, so every pre-existing consumer is unaffected.
  - **Multi-series matrix** (`ui/queries._matrix_rows`): the All-Values matrix keys each column by `(report_id, slot)` where `slot` is the report's distinct `(result_date, column_label)` sorted chronologically — NOT just `report_id`. A report with N result columns contributes N matrix columns (labels `dd.mm.yyyy`, deduped with `" (2)"`). `measurement_matrix` returns a 5-tuple `(lookup, disabled_lookup, ref_lookup, columns, col_labels)`; `all_values.py` and `detail.py` read `col_labels`. The Detail tab adds a `Messreihe`/`Series` column (`col_series`) only when a marker actually has >1 series in a report (`_series_labels`).
  - **`verify_extraction` job** (`llm_jobs._job_verify_extraction`, kind in `DATA_AFFECTING_KINDS`): re-sends each auditable report page image + the previous JSON to the LLM (`llm_client.verify_page_extraction`, temp 0) and asks ONLY whether every value came from the right column. `VerifyProblem`s map to pending findings via `_verify_problem_to_finding` (`source="verify"`): `value_from_reference_column` → `swap_value_ref_range`/`set_value`/`set_ref_range` (depends on what the auditor returned), `reference_holds_result` → registry-default `set_ref_range` or `clear_ref_range`, layout/series problems → `acknowledge`. Positional mapping: DataPoints ordered by id == extractor insertion order, so each page's non-empty entries map, in order, to the next `DataPoint` slice. Skips data points a pending `source="extraction"` finding already flags (no duplicate hint). All LLM calls happen BEFORE the write phase (delete `source=="verify"` for audited reports, then insert). Requires JSON `raw_text` + the PDF on disk; older flat-repr reports are skipped.
  - **Fix actions** (`database._apply_data_point_fix`): `set_value` (value-only, KEEPS the stored range — the auditor re-read the measurement without disputing it) and `swap_value_ref_range` (relaxed: either half is valid — value-only keeps the range, range-only keeps the value; only an entirely empty fix is rejected). `ui/tabs/mapping._finding_proposal` renders `set_value` and value-only swap without printing `> None`.
- **Manual correction (the human counterpart to accepting a finding)**: the Mapping tab's `st.dataframe` is an `st.data_editor` — editable **value / unit / reference** (TextColumn), everything else (date/report/original/canonical/registered/corrected) disabled. It is the ONLY place a user fixes a cell no automated check flagged. The write primitive is `database.update_data_point(session, dp_id, patient_id, *, value=_UNSET, unit=_UNSET, ref_range=_UNSET)` — `_UNSET` sentinel because **`None` is a meaningful CLEAR** (a qualitative row has no number, a report may print no range). Returns `{status: applied|unchanged|skipped|not_found, detail, changed}`; commits only on change. The seams:
  - **Patient-scoped in the write path, not trusted to the caller**: `report.patient_id` must equal the passed `patient_id` (else `skipped`) — the same multi-user rule the picker enforces everywhere else. `TestUpdateDataPoint.test_foreign_patient_row_rejected` pins it.
  - **`original_name` and the biomarker NAME are NOT editable here, on purpose.** `original_name` is the verbatim PDF spelling and the identity `_reapply_corrections` uses to find the row again after a reprocess deletes it — editing it orphans the correction. A NAME change belongs to the rename path, which records the old name as a registry **alias** so the next extraction resolves it automatically; a per-row name edit has no such anchor and the next reprocess undoes it.
  - **Field parsing reuses the ingestion helpers so a hand-edit can't drift from an extracted value**: value via `_parse_single_value` (German comma `13,18` ok; empty = clear; leading numeric run so a stray `13.18 mg/l` parses; **REJECTS a range-shaped cell** `5,0-10,0` → `skipped` "a range belongs in the reference field" — that is the value/reference column mix-up, taking its first bound would bake the misread back in). unit via `sanitize_unit` (drops a leaked `Unit`/placeholder → `skipped`, don't silently clear) → `canonicalize_unit` (registry snap, same call the extractor makes) → `_set_dp_unit` (**new shared helper extracted from the `set_unit` finding logic** so relabel-vs-convert can't diverge between the two paths: notation variant relabels, category error relabels via `_value_implausible_under_old_unit`, a real change converts). ref_range via `_parse_ref_range` (text or tuple; `<`/`>` one-sided — NOT `<=`; empty = clear; unparseable → `skipped`).
  - **A hand-edit supersedes a pending machine suggestion** about the same row: `_dismiss_findings_for_data_points` sets pending data-point findings targeting the row to `dismissed` (kept, not deleted — history still shows the pipeline suspected it). Sets `DataPoint.is_corrected = True`.
  - **`_recompute_abnormal` BUG fixed here**: it used to early-return when `value is None` or there were no bounds, **stranding a stale `is_abnormal=True`** on a cell the user had just emptied (a red badge on an empty cell). It now mirrors the extractor's `_is_value_abnormal` and CLEARS the flag. `is_abnormal` drives 🔴/🟢 in Detail/Trends/Overview and the abnormal queries in `ui/helpers.py`, so a stale flag is user-visible.
  - **Reprocess preserves manual edits** (`DataPoint.is_corrected` + `_migrate_data_point_corrected`): `_snapshot_reprocess` records a `corrected` dict keyed on **(filename, original_name, result_date_iso, column_label)** — the identity the extractor reproduces and the user cannot edit (NOT `(filename, original_name, unit)` like `_restore_disabled`, which breaks the moment the user fixes the unit). `_reapply_corrections` runs after `_restore_disabled_artifacts` and before the abort check, restoring value/unit/ref + `is_corrected` and recomputing `is_abnormal`; it reports `reprocess_corrections_reapplied` / `reprocess_corrections_lost` (**lost must be loud** — the re-extraction didn't reproduce that row, e.g. a misread original name). `_job_verify_extraction` skips `is_corrected` rows so the auditor never proposes overwriting a hand-fix. Pinned by `TestReprocessPdfs.test_reprocess_reapplies_manual_correction` / `test_reprocess_reports_lost_correction`.
  - **Editor re-render is keyed on `queries.cache_token()`** (editor + prev-snapshot session keys): a committed edit rebuilds the widget from DB truth; a **rejected** edit (`skipped`) disappears and shows `msg_edit_rejected` once instead of re-diffing forever. The tab diffs the editor against the seeded snapshot, calls `update_data_point` per changed row, then `refresh_patient_risk_flags` once (deterministic, no LLM).
  - **Every `data_point` finding gets an inline correction form** (`mapping._render_finding_correction`, condition `target_type=="data_point"` — NOT only `acknowledge`): an `acknowledge` finding (low confidence, the systematic value==ref-bound misread, a dropped result column) has NO fix the pipeline can apply, and a machine-applicable one (`set_unit`/`set_ref_range`/…) can still FAIL to apply (the stale post-rename proposal above), so in both cases the user needs somewhere to act on the evidence. The machine accept button is suppressed only for `action=="acknowledge"` (for it the button would always skip). The form renders, UNDER the source-page image, one prefilled value/unit/reference row per affected DataPoint (`queries.finding_data_points(finding_id)` — a `@st.cache_data` ORM-free `FindingValueRow` helper keyed on the cache token, so the suspect stored number is visible beside the scan it must be checked against) plus a save button. Saving routes each changed row through the SAME `update_data_point` primitive as the editor (so a range-in-value-cell is rejected the same way, the row gets `is_corrected`, and `_dismiss_findings_for_data_points` supersedes the finding). The accept-all loop SKIPS `acknowledge` findings (they'd only inflate the skipped count). `_ref_bounds`/`_series_caption` are shared module-level helpers so the form's prefilled range round-trips through `_parse_ref_range` and a multi-series finding labels which column each row came from. Pinned by `TestUiBehaviourAppTest.test_acknowledge_finding_shows_correction_form_not_fix_button` / `test_acknowledge_finding_correction_applies_and_dismisses` / `test_acknowledge_finding_rejects_range_in_value_cell` / `test_machine_finding_shows_both_fix_button_and_correction_form` (a `set_unit` finding renders BOTH `accept_finding_{fid}` and the `fix_val_{fid}_{dp_id}`/`fix_save_{fid}` form).
- **Health summary format** (`llm_client.PATIENT_SUMMARY_SYSTEM_PROMPT_DE/_EN`): prose-first, numbers-last. Structure: `### Gesamtbild` (3–5 plain sentences, no measurements unless one acutely critical value), `### Organsystem: <Name>` (1–2 plain sentences + ONE `> Belegende Werte: <Wert> <Einheit> (Ref. <niedrig>–<hoch>)` blockquote line), `### Trends & Verlauf`, `### Empfehlungen` (1–3 bullets). The ERZÄHLREGEL forbids numbers/units/abbreviations/ref-ranges in prose — they live only in the `>` blockquote lines. Rendered via `render_markdown_card(..., summary=True)` (adds `.bb-card--summary`; heading sizes, blockquote style, hidden anchor icons in `ui/cards.py` CSS). Stored summaries from BEFORE the prompt rewrite keep old list-style content — they render correctly but only a fresh "Zusammenfassung regenerieren" job produces the new format. `TestSummaryCardRendering` pins the helper, the prompt shape, and a regex guard against gluing markdown into an HTML string.
- **Cached UI reads** (`ui/queries.py`): every tab reads through cached helpers instead of inline ORM queries. Two rules: (1) helpers return **ORM-free namedtuples/scalars** — `st.cache_data` deep-copies its return value, so a detached ORM object raises on the second access; (2) every helper takes `cache_token()` as its first argument, which is `(database.commit_version(), PRAGMA data_version)`. `commit_version()` is an in-process counter bumped by an `after_commit` event listener; `data_version` alone misses commits made through the same connection, `commit_version` alone misses other processes — both are needed. Time-range sliders filter the cached rows **in Python** so dragging a slider never busts the cache. Column labels (`t("col_*")`) must be hoisted out of row loops: they were translated per row (31k `t()` calls per rerun at 7.2k data points, each one a session-state read).
- **Biomarker normalization**: 3-tier registry in `config.py` — canonical name → aliases + units + default ref range. Resolution order: exact match → alias match → fallback to original name.
  - **Hallucination guard** (`llm_client._filter_hallucinated_mappings`): `normalize_names` output is validated against the names actually shown to the LLM — a mapping whose `canonical` is neither a shown name nor an echo of its own `original` is dropped, so the LLM can never invent a phantom canonical that would split one marker into two.
  - **Unregistered markers** (names kept verbatim by tier 4): they get no default ref range and are invisible to critical-value/trend/cross-biomarker/missing-marker detection. The Mapping tab surfaces them (`_unregistered_markers`, mirroring the extractor's resolution tiers; user-added custom biomarkers excluded) with a warning + dataframe badge. Recovery: rename, or the data-quality check's `unknown` category → `register_biomarker` action (`database._apply_registry_fix` creates a registry row, only for names that actually have measurements; optional `params.ref_range` hint parsed via `_parse_ref_range`, unparseable hints ignored).
  - **Description prompts carry no canonical list**: `generate_biomarker_description` gets the marker's own units/default ref range from the registry (`_description_context_line`, `lang` passed explicitly — worker threads can't call `_get_lang()`) instead of a ~94-name list.
  - **Typo/OCR variants** (`Trigylceride`/`Tryglyceride` vs `Triglyceride`) are NOT caught at ingestion — every name path is exact-or-alias only, so each misspelling becomes its own canonical name. Detection happens in the data-quality check, and it is **deterministic first, LLM second**: `database.find_variant_candidates()` (pure `difflib`, keys via `_variant_key()` = base name lowercased/alnum-only) always produces the candidate pairs; `run_duplicate_check(..., candidates=)` renders them as "confirm or reject" hints, and **any candidate the LLM did not confirm is still emitted as a `merge` finding** — so a silent or failed duplicate-check call can no longer hide a duplicate. Four guards are mandatory because the curated registry itself contains 0.87–0.97 pairs of *different* markers: (1) the source must be non-curated (`_curated_name_keys()`) — blocks HDL/LDL/VLDL-Cholesterin, Freies T3/T4; (2) `_is_qualifier_pair()` rejects containment — blocks `Testosteron`⊂`Testosteron frei`, `Vitamin D2`⊂`Vitamin D (25-OH)`; (3) `_is_numbered_variant_pair()` requires equal digit runs — blocks `Interleukin 6`↔`Interleukin 8` (0.917, only IL-6 curated) and `Vitamin D2`↔`D3`; (4) names co-occurring in the **same report** are distinct markers and never paired. Measured: 53/53 single-char OCR typos of curated names pair correctly (100%), multi-char rewrites below 0.80 do not. Candidates also carry `source_units`/`target_units` (observed `DataPoint.unit`s); when those differ the finding appends `dq_candidate_merge_unit_warning` — merging only renames `canonical_name`, it never converts values. Accepted findings run `_merge_registry_rows()` (global migration + source kept as alias → durable); the Mapping tab's manual rename instead takes the per-patient `rename_canonical_name()` branch for non-registry names and records **no alias**, so the typo returns with the next PDF. Always follow a merge with backfill + risk refresh (unregistered names had no default ref range).
- **Unit conversion**: Single name-aware converter in `config._convert_ref_range(canonical_name, low, high, from_unit, to_unit)` — factors are keyed by (biomarker, unit pair) so shared pairs like mg/dl↔mmol/l resolve per biomarker (glucose ÷18 vs cholesterol ÷38.67). Returns `(None, None)` when unsupported; callers must treat that as "no range". Used by both `get_default_ref_range()` and `database.backfill_reference_ranges()`.
- **Cross-biomarker patterns**: Config-driven rules in `RISK_CONFIG["cross_biomarker_rules"]` detect correlated abnormalities (e.g., CK + Troponin → cardiac pattern). Severity can be upgraded or downgraded based on the pattern.
- **Deduplication**: PDFs skipped if SHA-256 hash already exists in `Report.file_hash`.
- **Auto-merge**: `database.auto_merge_biomarkers()` uses LLM to suggest canonical targets for variant groups; `apply_merge_plan()` executes (only merges when units compatible). **Currently has no UI entry point** — the `subheader_auto_merge`/`label_auto_merge_plan`/`btn_merge` translations are unused, so nothing calls it. It is also structurally useless for typos: `get_unique_biomarker_groups()` groups by exact `_canonical_base().lower()`, so `trigylceride`/`tryglyceride`/`triglyceride` land in three separate groups and are never candidates. Use the data-quality `merge` finding instead (see above).
- **Chat with your data** (`ui/tabs/chat.py`): free-form LLM Q&A per patient. A date-range slider (shared `_time_range_slider` helper, chat-scoped value key `chat_time_range_{patient.id}` so it's independent of the Trends/Overview slider; default = patient's full range) selects the window. `collect_chat_measurements()` returns ALL non-disabled, non-null measurements in that range (undated reports excluded) — deliberately uncapped, unlike the summary's `_collect_historical_data`. `format_chat_data_context()` renders profile + per-(biomarker,unit) chronological series into the system prompt. **Transcripts are DB-persisted** (`ChatConversation`/`ChatMessage`, cascade with patient delete, re-pointed on patient merge) — NOT session state: multiple conversations per patient (selectbox picker + "new conversation" + delete dialog), F5/restart-proof. The answer runs as an LlmJob kind `chat_answer` (question + context captured into `params_json` at submit; deliberately NOT in `DATA_AFFECTING_KINDS` — an app rerun would yank the user's tab). The tab's own polling fragment (`_poll_chat_answer`, wrapped in `@st.fragment(run_every=2)` **only while an answer is in flight** — see the polling rule under Background LLM jobs) shows progress and calls `adopt_chat_answer()` (idempotent via `ChatMessage.job_id`, unique per conversation) when the job finishes → survives tab switches AND F5. Failed/aborted answers leave the question as an unanswered user row (persistent warning; `build_llm_messages()` drops unanswered turns from the LLM payload except the trailing one). `chat_with_data()` still raises — the worker records it as job `error`. `clear_finished_llm_jobs()` adopts un-adopted done `chat_answer` results before deleting rows. Two selection keys: `chat_conv_{id}` (plain state, writable from body/callbacks) + `chat_conv_widget_{id}` (selectbox widget key) — Streamlit forbids writing a widget key from the body after the widget rendered.
- **Background LLM jobs** (`llm_jobs.py`): All long-running operations (process_pdfs, refresh_risks, regen_summary, bulk_descriptions, bulk_interpretations, backfill) run in daemon worker threads, NOT inline in the UI. Buttons call `submit_job(kind, label_key, params=...)` and return immediately; progress is persisted to the `llm_jobs` table and polled by the "LLM-Jobs" tab (`ui/tabs/llm_jobs.py`). Rules:
  - **Polling is gated**: all three `run_every=2` fragments (LLM-Jobs list, chat answer, the global running-jobs strip in `app.py`) are *defined* only while a job is actually pending/running — `get_active_llm_jobs()` for the jobs tab AND the strip, the tab's own `pending` flag for chat. The strip is informational + abort only (no transition detection — the jobs-tab poll exclusively owns flashing results and the app rerun, so two fragments can't race `st.rerun()` on one transition); its abort buttons use their own key space (`strip_abort_job_{id}`) because the jobs tab renders `abort_job_{id}` for the same job in the same rerun. `run_every` is baked into the decorator at definition time, so this needs two branches (polling fragment vs. plain render of the same body). An unconditional `run_every` re-executed forever AND re-registered a new browser `setInterval` on every full rerun (`cleanupAutoReruns` only runs on page change / new session), so an idle screen got steadily busier. When the last job finishes, the still-live poll triggers an app rerun; that rerun defines no polling fragment, and a leftover browser interval resolves to an unknown fragment id and is dropped server-side.
  - **Worker threads must NEVER touch `st.session_state`** — settings are captured as a snapshot at submit time into `LlmJob.config_json` and applied via `llm_client.set_job_config()` (thread-local); translations use `t(key, lang=...)` with the language from the snapshot.
  - **Kind locks**: one job per `(kind, patient_id)` at a time (`_active_kinds` is keyed by that tuple), so a kind offered from more than one tab (the UX rework deliberately moved several buttons between tabs — refresh_risks, regen_summary, bulk generation) can't double-run for the SAME patient, and patient A's running job never blocks patient B's button; `submit_job` returns `None` → UI shows `msg_job_already_running`. The `patient_id` is read from `params["patient_id"]` when not passed explicitly, so a call site can't forget it and share a lock slot with another patient.
  - **Stale marking**: `app.py` calls `mark_stale_llm_jobs_interrupted(session, exclude_ids=active_job_ids())` at module level — Streamlit re-executes it on EVERY rerun, so jobs with a live worker in this process are excluded (`llm_jobs._active_job_ids`). Best-effort (try/except): a DB lock must never crash the app view.
  - **Write locks & LLM calls**: `analyzer.refresh_risk_flags()` does its DELETE+INSERT AFTER the LLM call — never hold SQLite's single write lock across a slow HTTP request (UI reruns would hit "database is locked" after busy_timeout). Keep it that way in new work functions.
  - **Rerun trigger**: when a job in `DATA_AFFECTING_KINDS` transitions to done/error, the LLM-Jobs tab sets `st.session_state._rerun_requested = True` so main() reloads data.
  - **Job abort** (user action from the LLM-Jobs tab): per-job, NOT a global flag. `llm_jobs.abort_job(job_id)` marks the DB row (`LlmJob.aborted`) and calls `llm_client.request_job_abort(job_id)`, which adds the id to a module-level `_aborted_job_ids` set. Workers check `is_job_aborted()` (thread-local current job id, set via `set_current_job_id()`) between steps — `extractor.process_new_pdfs` breaks its PDF loop, `_run_bulk` breaks its item loop, `analyzer.refresh_risk_flags` skips the write phase. In-flight LLM calls fail fast: every call site passes `timeout=_abort_timeout() or _get_timeout()` (1s while aborted → `APITimeoutError`). `_run_job` then records status `"interrupted"` (not done/error) with `job_aborted_note`; partial results are kept. Job ids are unique, so finished entries never match a new job — no clearing needed.
  - **Reprocess is non-destructive** (`_job_reprocess_pdfs`): the delete-then-extract order is forced by the `file_hash` unique constraint, so the snapshot doubles as a restore payload — only reports whose PDF is on disk are deleted, `process_new_pdfs(force=True, only_files=targets)` stays scoped to exactly those files, and every deleted-but-not-re-extracted report is put back via `_restore_reports()` (per-PDF failure, abort, or a crash before the per-PDF loop). The snapshot/restore carries the column-aware fields too (`Report.result_dates`, `DataPoint.result_date`/`column_label`), and the delete clears `DataQualityFinding`s with `source in ("extraction","verify")` since a re-extract regenerates both. If nothing could be re-extracted the job **raises** (status `error`), because the returned `"error"` level is not mapped to job status — a returned `"error"` would still render as a green "done" row.
  - **Finished-job cleanup**: `database.clear_finished_llm_jobs(session)` deletes rows in done/error/interrupted state (returns count); the LLM-Jobs tab's "Clear finished" button calls it. Pending/running jobs are never touched.
  - **The strip must not move the tab bar**: it renders into an always-created `st.container()` slot so the tab bar's delta path never shifts when a job starts/finishes (see the tab-reset gotcha under Gotchas).
  - **Testing**: `submit_job(..., runner=llm_jobs._run_job)` runs the worker synchronously (no thread) — see `TestLlmJobs` and `TestLlmJobAbort`.

## Testing

```bash
python test_blutbild_buddy.py -v    # verbose
```

- Single file, `unittest`. Tests use temp dirs and mock LLM calls. The bottom `main()` builds an **explicit** suite — a new `TestCase` class that isn't added there silently never runs via `python test_blutbild_buddy.py`. `python -m unittest test_blutbild_buddy` discovers alphabetically instead, so run both: the orders differ and `st.session_state` is shared across tests (e.g. `TestExtractorMocked` pins `pdf_batch_size=0` because other classes leak `=1`).
- No fixture files or external services needed beyond Python packages.
- Test PDFs live in `reports_input/` (gitignored real data — a sample PDF is used for hash/page/image tests).
- **Behavioural UI tests** (`TestUiBehaviourAppTest`): run the real `app.py` with `streamlit.testing.v1.AppTest` against a temp DB, so a widget-level crash (stale multiselect default, unkeyed selectbox) shows up in `at.exception` instead of silently breaking the browser view. They set `config.DB_PATH`/`config.REPORTS_DIR` in `setUp` and restore them in `tearDown` — `app.py` runs in-process, so it reads the module-level paths. `AppTest` models `download_button` as an untyped element with no key, so match it by label.
